# 사쿠라이 마사히로 스타일 게임 개발 십계명

2026-09-21 · 사용자 제공 10계명 채택 · 한양 디펜스 개발/리뷰 적용

사용자가 전달한 제목과 10개 원칙을 보존하고 프로젝트 적용 방법을 정리했다. 제공문의 [1]~[64] 번호에 대응하는 참고문헌은 첨부되지 않았으므로 인물의 직접 발언·공식 지침으로 검증했다고 주장하지 않는다. 본 문서는 사용자가 채택한 개발 지침이다.

## 10계명과 프로젝트 적용

| ID | 원칙 | 실무 적용 | 확인 방법 |
|---|---|---|---|
| T-01 | **리스크와 리턴의 균형을 설계하라** | 강한 선택에는 물자·위치·시간·기회비용 등 대가를 정의. 외곽 화력 투자와 내곽 비축의 장단점, 합성 시 현재 방어 감소와 성장 이득을 설명 | 위험을 사전에 알 수 있는지, 다른 선택과 비교했을 때 얻고 잃는 것이 있는지 확인. 모든 행동에 새 페널티를 추가하지 않음 |
| T-02 | **스트레스와 해소의 흐름을 만들어라** | 접근/집결의 압박→병목 집중 사격→위협 감소→물자/다음 건설로 연결. 반복 실패·정보 부족을 긴장감으로 포장하지 않음 | 압박·해소·다음 목표가 나타나는 시점을 실제 플레이에서 기록. 경험치/새 스킬을 무조건 추가하지 않음 |
| T-03 | **타격감의 본질, 히트 스톱을 잊지 마라** | 적중 피드백의 짧은 정지·진동을 검토. 대규모 전투에서는 대상/효과의 국소 연출 우선, 피격 대상의 반응을 공격자보다 명확하게 | 연출 중 core 좌표·충돌·피격/공격 판정은 불변. 매 타격의 전역 정지로 입력·시뮬레이션·성능이 손상되지 않는지 검사. 전역 시간 조절은 별도 명세 필요 |
| T-04 | **입력 반응은 즉각적이어야 한다** | 입력 접수 시 선택 강조·고스트·구매/거절 피드백을 첫 가능한 표시 프레임에 제공. 장식 애니메이션 완료를 기다려 명령을 접수하지 않음 | 입력 접수→시각 피드백 지연을 정상 속도에서 측정. 실제 판정 확정 전 성공을 표시하지 않음. 낮은 FPS에서도 중복 구매/입력 유실 방지 |
| T-05 | **판정은 플레이어에게 유리하게, 연출은 과장되게** | 명료한 예고·선택 영역·스냅·미리보기로 기대와 판정을 맞춤. 공격/피격 영역의 관대함과 과장 포즈는 해당 전투 명세에 따라 적용 | 화면상의 가능/불가와 실제 결과 일치. 기존 사거리·폭발 반경·20px 셀/40px 점유를 몰래 확대하지 않음. hitbox 변경은 밸런스 결정/회귀와 함께 처리 |
| T-06 | **느린 것은 죄다, 모든 속도를 끌어올려라** | 불필요한 로딩·메뉴 전환·결과 대기·재시작 지연을 줄임. 템포의 목적은 조작 의욕 유지 | 메뉴/재시작 시간과 입력 가능 시점 확인. 전략 판단 시간·위협 예고·필수 입력 해제 펜스를 없애거나 게임 전체를 무조건 가속하지 않음 |
| T-07 | **개성을 살리는 ‘울퉁불퉁한’ 밸런싱** | 시설별 강점/약점을 분리. 화차·장승·봉수·혼천의의 역할과 병기별 유효 지형을 강화하는 방안부터 비교 | 같은 시나리오에서 서로 다른 전략의 성과와 손실 확인. 항상 우월한 전략/악용은 수정 대상이며 필요하면 하향도 가능 |
| T-08 | **보상(Gifts)은 초기 단계부터 설계하라** | 재화 획득과 소비를 함께 설계. 선택 시설 비용·현재 물자·부족액·다음 목표를 명확히 표시하고 획득 피드백 제공 | 보상을 얻은 뒤 원하는 행동이 생기는지 확인. 해금/컬렉션/경험치는 해당 WP가 승인한 경우만 도입 |
| T-09 | **개발자의 사정을 플레이어에게 강요하지 마라** | 사용자 화면은 플레이에 필요한 언어로 설명. 상태/거절 원인을 전달하고 디버그 정보는 별도 표시. 이미 이긴 전투를 연출 진행 때문에 강제 패배시키지 않음 | 실제 성공/실패가 결과·연출과 일치. 성문 파괴와 외곽 붕괴 구분. 검증용 강제 붕괴는 시험에서만 사용하고 일반 플레이에 노출하지 않음 |
| T-10 | **코드는 합리적이고 명확하게 관리하라** | 새 파일/라벨은 역할을 드러내는 일관된 명명 사용, 불명확한 일본어 로마자 표기 회피. 조정 수치는 config/검증된 데이터로 분리하고 결정·담당·근거를 공유 | 기획자가 수치 위치와 의미를 찾고 동일 설정을 재현할 수 있는지 확인. 기존 `config.gd`/설정 경로 활용, Excel 파이프라인·대규모 이름 변경은 필요할 때만 별도 도입 |

거리 기반 공격 보너스, 전역 히트 스톱, 새로운 보상 종류 등 제공문의 구현 팁은 후보 기법이다. 장르와 현재 WP에 맞는 수단을 선택하며 모든 팁을 동시에 구현하는 요구로 해석하지 않는다.

## 적용 프로세스

### 1. 기획 / READY

GPT가 목표 플레이 경험 1문장, 관련 T-ID, 위험/보상, 입력→피드백, 보상→다음 행동, 비범위를 작성한다. 모든 WP에 10개를 기계적으로 강제하지 않는다. 관련 없는 항목은 이유를 적고 비해당 처리. 새 수치 기준이나 게임 규칙 변경은 구현 전 WP/DECISIONS에 명시하고 기존 AC를 소급 변경하지 않는다.

### 2. 구현 계획 / IN_PROGRESS

Claude가 관련 원칙을 코드·UI·설정 데이터·시험에 연결한다. 예: 건설 입력→비용 검증/원자적 차감→즉시 성공/거절 표시. 보이는 연출과 core 상태는 분리한다. 미결정 항목은 영향·권고안·재평가 조건을 함께 기록하며, 범위 안의 가역적인 기술 선택은 근거를 남기고 진행한다.

### 3. 검증 / 실제 실행

변경 영향에 맞는 자동 시험→실제 실행/캡처→수정 순서. UI·아트는 실제 표시 크기와 지원 해상도로, 입력·템포는 정상 속도로 확인한다. 효과 변경은 판정 불변과 부하/성능을 확인한다. 정적 캡처만으로 지연·손맛·체감 재미를 PASS 처리하지 않는다. 구현 SHA·release 해시·seed·설정·실행 방식과 증거를 연결하고 이전 증거를 보존한다.

### 4. 리뷰 / REVIEW

GPT가 [게임 평가 지침](GAME_EVALUATION_GUIDE.md)과 함께 검토한다. 기능 정확성은 기존 AC의 PASS/FAIL/NOT RUN, 10계명의 체감 효과는 충족/보완 필요/미평가/비해당으로 분리한다. 각 지적은 **관찰 사실 → 플레이어 영향 → 개선안 → 재검증** 형식으로 작성하고 다음 1~3개를 우선순위로 제시한다.

### 5. 완료 / 다음 작업

기존 필수 AC와 GPT 판정을 따라 DONE 여부를 결정한다. 미평가 원칙을 완료로 위장하지 않으며 모든 원칙의 미평가가 자동으로 해당 WP의 실패라는 뜻도 아니다. 수용 기준에 포함된 항목은 반드시 충족해야 한다. 규칙 변경은 별도 WP/결정, 비범위 개선은 후속 backlog로 전달한다. 새 승인 단계나 불필요한 반복 회의는 추가하지 않는다.

- WP-005 게임샷: T-03/04/05/09. 실제 크기에서 명중/상태/배치 피드백, 연출과 판정 분리. 기존 V-01~04 순서 유지.
- WP-009 성밖·성문: T-01/02/06/09. 접근 예고·공방의 긴장과 해소, 지킨 성문을 시나리오 때문에 강제 파괴하지 않음.
- WP-010 장승 파괴: T-01/02/05/07. 공성 적의 사전 식별·대응 기회와 장승의 유도 역할 유지.
- 랜덤 보급/합성: T-01/07/08을 적용할 기획 후보. 이 문서 저장을 새 랜덤 모드 구현 승인으로 간주하지 않음.
